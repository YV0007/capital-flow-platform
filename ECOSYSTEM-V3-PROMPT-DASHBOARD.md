## Что меняется относительно v2

1. **`anchor: "nvidia"` заменяется на `pivots: [id, id, …]`.** 26 записей: 25 из
   документа-блюпринта плюс ARM (документ сам называет его опциональным 26-м — включаем,
   он уже полностью исследован). Соответствие пивотов и уже существующих `id` в
   `nvidia_ecosystem.json` — см. §«Соответствие пивотов» в промпте движка; почти все
   совпадают напрямую, разночтений нет.

2. **Правило включения ослабляется с «≤2 шагов от единственного якоря» на «≤2 шагов от
   ЛЮБОГО пивота».** Сущность, не дотягивающаяся до ни одного из 26 пивотов за два шага,
   в файл не входит — как и в v2, просто мера теперь коллективная, а не одноточечная.

3. **У каждой сущности — новое булево поле `pivotal`.** `true` для 26 пивотов, `false`
   для всех остальных (secondary/tertiary в терминах блюпринта).

4. **Два новых типа связи**, оба по правилам evidence/tier контракта v2:
   - `is_alternative_to` (хребет `rivalry`) — жизнеспособный путь-замена существует,
     это не активная конкуренция (пример: JAX — жизнеспособная альтернатива PyTorch,
     хотя JAX не «конкурирует» с PyTorch в смысле рынка).
   - `enables_interop` (хребет `physical`) — стандарт позволяет двум иначе раздельным
     стекам разговаривать (пример: ONNX между PyTorch- и не-PyTorch-инференсом, если
     найдётся источник).

5. **Центральность — считает движок, не агент.** На каждой сущности:
   ```jsonc
   "centrality": { "degree": 24, "betweenness": 0.083 }
   ```
   `degree` — число уникальных сущностей, с которыми есть ребро. `betweenness` —
   стандартная betweenness centrality по неориентированному графу (networkx или
   эквивалентный алгоритм на чистом Python — граф на **сотни** узлов, точность важнее
   производительности).

6. **Новый блок на уровне всей сети**, а не сущности:
   ```jsonc
   {
     "network": {
       "totalNodes": 118,
       "totalEdges": 260,
       "pivotalNodes": 26,
       "secondaryNodes": 92,
       "density": 0.037,
       "averageDegree": 4.4,
       "clusteringCoefficient": 0.21,
       "singlePointsOfFailure": [
         { "id": "tsmc", "reason": "убрать — рвутся 40% путей между хребтами железа и лабораторий", "betweenness": 0.31 }
       ],
       "subgraphs": [
         { "id": "gpu-ecosystem", "label": "GPU-стек",
           "description": "Обучение и инференс на GPU: NVIDIA, AMD, PyTorch, CUDA, покупатели-гиперскейлеры",
           "nodeIds": ["nvidia","amd","pytorch","cuda", "…"],
           "edgeIds": ["…"] },
         { "id": "tpu-ecosystem", "label": "TPU-стек",
           "description": "Google, DeepMind, JAX, Google Cloud — вертикально интегрированная альтернатива",
           "nodeIds": ["google","google-deepmind","jax","google-cloud"],
           "edgeIds": ["…"] },
         { "id": "infrastructure-backbone", "label": "Хребет инфраструктуры",
           "description": "Производство и геополитика, общие для обоих стеков",
           "nodeIds": ["tsmc","asml","synopsys","cadence","arm","taiwan","usa","brookfield"],
           "edgeIds": ["…"] }
       ]
     }
   }
   ```
   `singlePointsOfFailure` — не топ-N по критичности (это уже есть в `criticality`), а
   узлы с непропорционально высокой betweenness относительно их слоя: убери — и сеть
   рвётся на несвязные куски там, где раньше был один путь. Три подграфа — стартовый
   набор из блюпринта; движок вправе не находить какой-то из них пустым, если данные не
   подтверждают деление (например, если у «TPU-стека» на деле нет самостоятельного
   ландшафта — сказать об этом в журнале, а не подгонять список узлов).

7. **Версионирование и changelog по 10 категориям блюпринта.** Первый выпуск — `v1.0-<YYYY-MM>`
   (не diff против пустоты — фиксируется как есть). `changelog` содержит те же 10
   категорий, что и в блюпринте (новые узлы · удалённые · связи+ · связи− · связи~ ·
   сдвиг критичности >5 · смена фазы · эскалация риска · новые источники · смена слоя),
   даже если в первом выпуске часть категорий пуста.

## Что НЕ меняется и не пересчитывается

- 16 слоёв, 5 хребтов, рубрика критичности, тиры, правило подтверждения — **дословно

## 1. Адаптер — `src/data/aiEcosystemNetwork.js`

Новый файл, по образцу `nvidiaEcosystem.js` (не копия — читает новый контракт).
Добавляет к прежним экспортам:

- `PIVOTS` — множество из `raw.pivots` (или из сущностей с `pivotal: true`, если поле
  `pivots` на уровне файла не пришло — оба варианта контракт допускает).
- `CENTRALITY_META` — как читать/подписывать `degree`/`betweenness`, коротким
  русским пояснением каждого в тултипе.
- `SUBGRAPH_META` — id → русская подпись → цвет акцента для подсветки при включённом
  подграфе.
- `NETWORK_META` — плотность, средняя степень, кластеризация — для отдельной панели
  сводки сети (см. ниже).

Как и раньше: адаптер ничего не считает, только читает то, что посчитал движок (или
твой фикстурный скрипт на этапе 0).

## 2. Генерализация якоря — везде, где код говорил «NVIDIA», теперь говорит «пивот»

- В раскладке (`ecoLayout.js`): там, где сейчас есть любая логика вида «якорь всегда
  виден с подписью», распространи её на все сущности с `pivotal: true` — не только
  одну. Геометрия (ядро/орбита/дуга) не меняется, меняется только правило, кто получает
  привилегию подписи на любом зуме.
- В плитке: пивот получает лёгкий визуальный маркер (тонкая рамка или засечка,
  **не новый цвет** — цвет уже занят слоем/хребтом) с тултипом «пивотный узел сети».
- В фильтр-баре — новый переключатель «только пивоты / вся сеть».

## 3. Подграфы — новая линза, по образцу существующих

Третья линза рядом с «Круги»: **«Подграфы»** — выбор одного из трёх (GPU-стек / TPU-стек
/ хребет инфраструктуры) подсвечивает его узлы и рёбра, остальное гаснет тем же
паттерном, что уже есть у выбора компании («убирает остальное совсем, а не
приглушает» — правило из README действует и здесь). Подпись подграфа и его
`description` — в шапке линзы.

## 4. Точки отказа — используй существующий паттерн подсветки

`network.singlePointsOfFailure` — не новая механика, а применение уже существующего
приёма (как критичные узлы уже читаются по размеру плитки): добавь тонкое кольцо или
пунктирный ободок вокруг узлов из списка, с тултипом, показывающим `reason` из данных
дословно. Не изобретай новый цвет специально под это — красный уже занят хребтом
`control`, зелёный — `moat`; используй нейтральный контурный акцент (например,
пунктирная обводка без заливки).

## 5. Панель сводки сети — новый, лёгкий компонент `ecosystem/NetworkSummary.jsx`

Небольшая панель (не модалка, не блокирует карту) с `totalNodes` / `totalEdges` /
`pivotalNodes` / `density` / `averageDegree` / `clusteringCoefficient` — по образцу
существующей плашки итогов сверху карты (`+N слоёв · N кругов`, видна на скриншоте
из этой сессии). Продли эту же строку, не строй отдельный блок: `26 пивотов · N
подграфов · N точек отказа`.

## 6. Панель сущности — одна добавка

В `EcoEntityPanel.jsx`, в блок гравитации (уже существует), добавь строку
`centrality`: степень и betweenness с однострочным пояснением каждой («сколько прямых
связей» / «сколько кратчайших путей через эту сущность»). Признак пивота — бейджем
рядом с именем, как и `stale`.

## 7. Что осознанно НЕ строится в этом заходе

- Временная шкала/слайдер версий, diff между `vX` и `vY`, тренд-график критичности —
  всё это требует 2+ реальных версий файла, которых пока нет. Оставь заготовку в
  README (раздел «Отложено до Phase 4») вместо кода.
- Отдельный экран «уязвимости сети» — точки отказа встроены в существующую карту
  (шаг 4), отдельный dashboard-экран не нужен, пока сеть не выросла за пределы того,
  что помещается на одной карте.
