Пользователь передал документ **«Complete AI Infrastructure Ecosystem Mapping
Blueprint»**, сохранённый в `ab-investment/ECOSYSTEM-V3-BLUEPRINT.md`. Прочитай его

ландшафт железа, софта, лабораторий и политики, который называет этот документ.

**Значит, задача — не «исследуй 25 компаний заново».** Задача в три части:

1. **Дозаполнить рёбра между пивотами, которые не проходят через NVIDIA.** Смысл всего
   документа — «AMD конкурирует с NVIDIA, но оба зависят от TSMC»: связи между
   НЕ-NVIDIA пивотами, которые пилот не собирал специально, потому что искал только
   соседей NVIDIA. Из 325 возможных пар пивотов уже есть 53 ребра (см. §«Соответствие
   пивотов» ниже — они наследуются из `nvidia_ecosystem.json` без изменений). Остальные
   272 пары **в большинстве не имеют реальной связи и не должны её получить** — включать
   ребро туда, где его нет, нарушает уже действующее правило контракта v2 «нет цитаты —
   нет ребра». Не превращай это в матричный обход всех 325 пар: см. §«Что реально
   исследовать» — конкретный список из 11 пар плюс один проход на честноту по каждому
   пивоту (не по каждой паре).
2. **Добавить одну сущность** — `google-cloud`, отдельно от `google`/`google-deepmind`.
3. **Посчитать сетевые метрики**, которых не было в схеме с одним якорем: центральность,
   точки отказа, подграфы. Это чистый Python поверх уже собранного графа, без единого

## Что меняется относительно v2

1. **`anchor: "nvidia"` заменяется на `pivots: [id, id, …]`.** 26 записей: 25 из
   документа-блюпринта плюс ARM (документ сам называет его опциональным 26-м — включаем,
   он уже полностью исследован). Соответствие пивотов и уже существующих `id` в
   `nvidia_ecosystem.json` — см. §«Соответствие пивотов» в промпте движка; почти все
   совпадают напрямую, разночтений нет.

2. **Правило включения ослабляется с «≤2 шагов от единственного якоря» на «≤2 шагов от
   ЛЮБОГО пивота».** Сущность, не дотягивающаяся до ни одного из 26 пивотов за два шага,
   в файл не входит — как и в v2, просто мера теперь коллективная, а не одноточечная.

3. **У каждой сущности — новое булево поле `pivotal`.** `true` для 26 пивотов, `false`
   для всех остальных (secondary/tertiary в терминах блюпринта).

4. **Два новых типа связи**, оба по правилам evidence/tier контракта v2:
   - `is_alternative_to` (хребет `rivalry`) — жизнеспособный путь-замена существует,
     это не активная конкуренция (пример: JAX — жизнеспособная альтернатива PyTorch,
     хотя JAX не «конкурирует» с PyTorch в смысле рынка).
   - `enables_interop` (хребет `physical`) — стандарт позволяет двум иначе раздельным
     стекам разговаривать (пример: ONNX между PyTorch- и не-PyTorch-инференсом, если
     найдётся источник).

5. **Центральность — считает движок, не агент.** На каждой сущности:
   ```jsonc
   "centrality": { "degree": 24, "betweenness": 0.083 }
   ```
   `degree` — число уникальных сущностей, с которыми есть ребро. `betweenness` —
   стандартная betweenness centrality по неориентированному графу (networkx или
   эквивалентный алгоритм на чистом Python — граф на **сотни** узлов, точность важнее
   производительности).

6. **Новый блок на уровне всей сети**, а не сущности:
   ```jsonc
   {
     "network": {
       "totalNodes": 118,
       "totalEdges": 260,
       "pivotalNodes": 26,
       "secondaryNodes": 92,
       "density": 0.037,
       "averageDegree": 4.4,
       "clusteringCoefficient": 0.21,
       "singlePointsOfFailure": [
         { "id": "tsmc", "reason": "убрать — рвутся 40% путей между хребтами железа и лабораторий", "betweenness": 0.31 }
       ],
       "subgraphs": [
         { "id": "gpu-ecosystem", "label": "GPU-стек",
           "description": "Обучение и инференс на GPU: NVIDIA, AMD, PyTorch, CUDA, покупатели-гиперскейлеры",
           "nodeIds": ["nvidia","amd","pytorch","cuda", "…"],
           "edgeIds": ["…"] },
         { "id": "tpu-ecosystem", "label": "TPU-стек",
           "description": "Google, DeepMind, JAX, Google Cloud — вертикально интегрированная альтернатива",
           "nodeIds": ["google","google-deepmind","jax","google-cloud"],
           "edgeIds": ["…"] },
         { "id": "infrastructure-backbone", "label": "Хребет инфраструктуры",
           "description": "Производство и геополитика, общие для обоих стеков",
           "nodeIds": ["tsmc","asml","synopsys","cadence","arm","taiwan","usa","brookfield"],
           "edgeIds": ["…"] }
       ]
     }
   }
   ```
   `singlePointsOfFailure` — не топ-N по критичности (это уже есть в `criticality`), а
   узлы с непропорционально высокой betweenness относительно их слоя: убери — и сеть
   рвётся на несвязные куски там, где раньше был один путь. Три подграфа — стартовый
   набор из блюпринта; движок вправе не находить какой-то из них пустым, если данные не
   подтверждают деление (например, если у «TPU-стека» на деле нет самостоятельного
   ландшафта — сказать об этом в журнале, а не подгонять список узлов).

7. **Версионирование и changelog по 10 категориям блюпринта.** Первый выпуск — `v1.0-<YYYY-MM>`
   (не diff против пустоты — фиксируется как есть). `changelog` содержит те же 10
   категорий, что и в блюпринте (новые узлы · удалённые · связи+ · связи− · связи~ ·
   сдвиг критичности >5 · смена фазы · эскалация риска · новые источники · смена слоя),
   даже если в первом выпуске часть категорий пуста.

# ДЕТЕРМИНИРОВАННЫЙ СЛОЙ — `engine/nvnet_*.py`

- `nvnet_ingest.py` — читает `handoff/nvidia_ecosystem.json` как семя (все 106 сущностей,
  243 связи копируются без изменений, кроме простановки `pivotal: true/false`), плюс
  новые CSV из частей А и Б выше (тот же формат `entities.csv`/`edges.csv`/`sources.csv`,
  что в промпте v2), плюс профиль `google-cloud`.
- `nvnet_centrality.py` — degree и betweenness по неориентированному графу. Библиотеки
  нет в проекте — либо `pip install networkx` (проверь, что это не ломает остальной
  конвейер), либо чистый Python (Брандес для betweenness на графе в пару сотен узлов —
  секунды, не проблема). Пиши в `centrality` каждой сущности.
- `nvnet_subgraphs.py` — три подграфа блюпринта (`gpu-ecosystem`, `tpu-ecosystem`,
  `infrastructure-backbone`) правилом по `role`/`sector`/`layer`, не вручную построенным
  списком: если правило даёт пустой или вырожденный подграф (например, у TPU-стека нет
  самостоятельного ландшафта отдельно от Google) — зафиксируй в журнале, не подгоняй
  список узлов, чтобы подграф выглядел содержательным.
- `nvnet_spof.py` — точки отказа: сущности с betweenness в верхнем дециле относительно
  сущностей своего слоя. Не то же самое, что топ по критичности — критичность уже есть
  в данных, это про структурную позицию в графе, а не про важность самой по себе.
- `nvnet_handoff.py` — сборка `handoff/ai_ecosystem_network.json` по контракту, первая
  версия `v1.0-<месяц-прогона>`, `changelog` по 10 категориям блюпринта (для первого
  выпуска большинство «изменено относительно предыдущей версии» полей пуст — это
  ожидаемо, не первый месяц эволюции, а первый выпуск сети). Валидатор на выходе, как
  в v2: файл, не прошедший контракт v3, не пишется.
